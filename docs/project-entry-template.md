# 프로젝트 항목 작성 형식

`/projects/[slug]`는 사실상 이력서로 쓰인다. 이 문서는 `scripts/seed-projects.ts`의
`overviewMd`를 쓸 때 따르는 공통 형식이다. 새 프로젝트를 추가할 때 이 문서만 보고 쓸 수 있어야 한다.

## 전제 — overviewMd가 담당하지 않는 것

상세 페이지(`app/projects/[slug]/page.tsx`)는 `overviewMd`를 `## 프로젝트 개요` 아래
통째로 렌더한다. 그 위/옆이 이미 아래를 담당하므로 **본문에서 반복하지 않는다.**

| 항목 | 담당 |
|---|---|
| 기간·팀·역할·링크(데모/저장소/스토어) | 사이드바 (구조화 필드) |
| 기술 스택 | 본문 위 `## 사용 기술` 섹션 (`stack` 필드) |
| 한 줄 소개 | 카드/헤더의 `summary` 필드 |

## 헤딩 순서 (고정)

```
(리드 문단 — 헤딩 없음)
## 맡은 일
## 주요 기능
## 설계 판단        ← 대표 티어만
## 문제 해결
## 성과와 한계
## 스크린샷
```

순서를 바꾸지 않는다. 항목 간 비교가 가능해야 형식을 정한 의미가 있다.

## 티어

같은 헤딩 순서를 쓰되 분량을 달리한다. 실무 경력과 습작을 같은 분량으로 두면 변별력이 죽는다.

| 티어 | 대상 | `## 설계 판단` | `## 문제 해결` |
|---|---|---|---|
| 대표 | 실무 경력, 깊게 판 개인 프로젝트 | 2~4개 | 2~3개 |
| 압축 | 습작, 단기 프로젝트 | 생략 | 1개 |

## 섹션별 작성 기준

### 리드 문단 (헤딩 없음, 2~3문장)

무엇을, 누구를 위해, **지금 어떤 상태인지**(운영 중/출시/중단). `summary`보다 한 단계 구체적으로.

### `## 맡은 일` (3~5줄)

팀 안에서의 경계. **내가 하지 않은 것도 적는다.**

- 팀 프로젝트: 기획·디자인·백엔드가 따로 있으면 명시한다. 없으면 기여도가 부풀려 읽히거나
  반대로 통째로 의심받는다.
- 1인 개발: "혼자"로 끝내지 말고 어느 범위까지 직접 했는지 쓴다. 가져다 쓴 것(디자인 시스템,
  템플릿)이 있으면 밝힌다 — 과장이 없으면 나머지 서술의 신뢰도가 올라간다.

### `## 주요 기능` (3~6개, 각 한 줄)

**상한을 지킨다.** "다 했다"가 아니라 "이게 핵심이다"로 읽혀야 한다. 기능 이름만 나열하지 말고
그 기능이 무엇을 해결하는지가 한 줄에 들어가게 쓴다.

### `## 설계 판단` (대표 티어만, 2~4개)

**이 형식의 핵심.** 항목마다 네 요소를 한 문단에 담는다.

```
상황/제약  →  고려한 대안  →  선택과 이유  →  결과
```

**대안이 없었던 것은 넣지 않는다.** 고민 없이 정해진 건 설계 판단이 아니라 그냥 구현이다.

- 나쁨: "TanStack Query를 사용해 서버 상태를 관리했습니다." (대안도 이유도 결과도 없음)
- 좋음: "태그를 클릭할 때마다 Mongo를 다시 왕복해 프로덕션에서도 140~250ms가 걸렸다.
  서버 페이지네이션을 유지할지, 전체를 한 번만 받아 로컬에서 거를지 저울질했고, 글이 수십 편
  규모라 후자를 골랐다. 클릭 반응이 즉시로 바뀌었고, 대신 글이 크게 늘면 되돌려야 한다는
  전제를 코드에 남겨뒀다."

### `## 문제 해결` (대표 2~3개 / 압축 1개)

```
증상  →  원인을 규명한 방법  →  해결  →  확인된 효과
```

**"규명한 방법"이 이 섹션의 값어치다.** 무엇을 측정했고 무엇으로 가설을 배제했는지가 없으면
그냥 버그 수정기다. 처음 세운 가설이 틀렸다면 그것도 쓴다 — 틀린 가설을 배제한 과정 자체가 실력이다.

### `## 성과와 한계` (3~5줄)

숫자가 있으면 숫자로, 없으면 정직한 상태 서술로. **숫자를 지어내지 않는다.**
개인 프로젝트의 방문자 수처럼 작은 숫자는 적지 않는 편이 낫고, 대신 운영 중 실제로 발견하고
해결한 장애처럼 규모와 무관하게 유효한 사실을 쓴다.

**한계 또는 다음에 할 것을 반드시 한 줄 포함한다.** 자기 코드의 약점을 말할 수 있다는 것
자체가 신호이고, 없는 성과를 만드는 것보다 훨씬 안전하다.

### `## 스크린샷`

`![설명](/projects/<slug>/<파일>.webp)` 형식. 3~4장.

## 작성 절차

기억에만 의존하지 않는다. 근거를 먼저 모으고, 기억은 그 근거를 놓고 되살린다.

```
A. 근거 수집   git 이력 + 저장소 문서 + AI 대화 로그에서 소재 후보 목록화
B. 골격 초안   자동 수집분만 채우고 기억이 필요한 자리는 비워둠
C. 인터뷰      비운 자리를 3~5개씩 질문 (2~3라운드)
D. 본문 작성   overviewMd 작성 후 검수
E. 반영        seed-projects.ts 수정 → npm run seed:projects
```

### 섹션별 근거 위치

| 섹션 | 자동 수집 | 기억에서만 |
|---|---|---|
| 리드 문단 | README, 기존 `summary` | 현재 운영 상태, 사용자 규모 |
| 맡은 일 | `git log --author`, 디렉터리별 커밋 분포 | 협업 방식, 내가 안 한 것 |
| 주요 기능 | `feat:` 커밋, README | 무엇이 핵심인지의 판단 |
| 설계 판단 | `docs:` 커밋, `docs/worklog/*.md`의 `배경`, CHANGELOG `이전 상태`, AI 로그 | 판단의 진짜 이유, 조직적 제약 |
| 문제 해결 | CHANGELOG `이전 상태`+`검증`, AI 로그 디버깅 세션 | 왜 그 가설을 먼저 의심했는지 |
| 성과와 한계 | — | 전부 |

### AI 대화 로그 활용

`~/.claude/projects/<경로-슬러그>/*.jsonl`:

- `type: "ai-title"` — 세션 주제 요약. 수십 MB를 다 읽지 않고 주제 색인을 만드는 값싼 경로.
- `type: "user"` 중 `message.content`가 문자열이고 `<`로 시작하지 않는 것 — 사용자가 직접
  타이핑한 발화. 의사결정의 갈림길("A랑 B 두 가지가 있지?")이 그대로 남아 있어 **설계 판단**의 원재료다.

저장소 문서라고 다 같은 값어치가 아니다. 빌드 에러·캐시 정리 런북(`troubleshooting.md` 류)은
이력서 가치가 낮다. 요구사항 변경과 대안 검토가 남은 작업 로그가 진짜 재료다.

### 인터뷰 원칙

빈칸을 던지지 않는다. **근거를 먼저 제시하고 그때의 판단을 묻는다.**

- 나쁨: "어떤 기술적 결정을 하셨나요?"
- 좋음: "8월 27일 로그에 소셜 로그인이 카카오→네이버로 바뀌었고 카카오 문서를 `legacy/`로
  남기셨습니다. provider 무관하게 설계해둔 게 전환비용을 줄인 걸로 보이는데, 처음부터 교체
  가능성을 염두에 두신 건가요, 결과적으로 그렇게 된 건가요?"

"기억 안 난다"도 유효한 답이다. 그 항목은 비우고 넘어가지, 추측으로 채우지 않는다.
숫자는 근거 자료에서 나온 것이라도 반드시 확인을 거친다.

## 슬러그 주의

`scripts/seed-projects.ts`는 `deleteMany({ slug: { $nin: currentSlugs } })`로 배열에 없는
슬러그를 지운다. **기존 슬러그의 이름을 바꾸면 문서가 지워지고 URL이 죽는다.** 항목을 나눌 때는
기존 슬러그를 유지한 채 새 슬러그를 추가한다.
